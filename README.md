# Auditoría incremental de enlaces UPV

La **portada es el nivel 0 y la única semilla**. Cada salto a una página de `upv.es` o cualquiera de sus subdominios añade un nivel. Los enlaces externos se comprueban como destinos HTTP(S), pero sus páginas no se añaden a la cola ni se analizan sus enlaces. El mapa web solo entra en el rastreo si se puede alcanzar desde la portada, al nivel que corresponda. SQLite guarda el menor nivel conocido de cada página, sus enlaces, los resultados de comprobación y la ronda completada. `level_schedule = 0:1;1:1;2:1;3:4` programa rondas diarias para los niveles 0, 1 y 2, y una ronda cada cuatro días para el nivel 3. Una ronda nueva empieza cuando termina la anterior y ha transcurrido el intervalo desde su comienzo. Una página **se rastrea una sola vez por ronda de su nivel** aunque otros enlaces vuelvan a señalarla. Las comprobaciones inciertas de enlaces se guardan en `pending_links` y se reintentan sin descargar otra vez la página de origen.

La raíz habitual se indica con `crawl.start_url`. Para un rastreo adicional desde otro subdominio o página UPV, `--start-url https://etsit.upv.es/` la convierte en nivel 0. La opción crea automáticamente una base SQLite y una carpeta de informes independientes (nombre derivado del dominio y la URL); no altera la ronda de la portada. Desde esa nueva raíz se siguen enlaces a cualquier subdominio de `upv.es` hasta el nivel configurado, y los externos solo se comprueban. Si se cambia `start_url` dentro de un `config.ini` existente sin usar `--start-url`, el programa rechaza reutilizar una base de datos cuyos niveles se calcularon desde otra raíz.

Cada ejecución revisa **hasta 10.000 páginas** por defecto, incluyendo las que descubra durante ese mismo lote, y entrega **un correo por destinatario** con dos CSV: uno agrupado por URL de destino exacta y resultado HTTP, y otro con todas las apariciones por página de origen. El correo se envía al terminar la **ejecución**, aunque la ronda de un nivel siga abierta; por tanto, sus cifras no son el acumulado de la ronda. La cabecera indica el motivo del fin (tiempo, límite de páginas intentadas, límite de solicitudes HTTP o ausencia de páginas listas), las páginas intentadas en total y, por nivel y día, **destinos distintos, apariciones y páginas afectadas**. Luego muestra grupos compartidos y una muestra de incidencias aisladas; `max_inline_groups = 30` controla el total mostrado. Un informe vacío solo indica que no se encontraron enlaces rotos en las páginas procesadas. Se comprueban los enlaces de las páginas de niveles 0 a 3, incluidos los que apuntan a nivel 4; las páginas de nivel 4 no se rastrean. Una página puede recibir una petición al comprobarla como enlace y otra al rastrearla; solo la segunda analiza sus enlaces. Los resultados válidos se reutilizan durante `link_ttl_days = 1`; los fallos inciertos se reintentan.

`mail.subdominios` enruta cada incidencia **según el dominio de la página de origen**, nunca según el destino roto. Ejemplo: `subdominios = alumni.upv.es:alumni@example.org, cfp.upv.es:cfp@example.org`. El dominio configurado y sus hijos se asignan al destinatario indicado; si hay entradas solapadas gana la más específica. Los dominios que comparten dirección se reúnen en un correo. `mail.recipients` recibe el resto de UPV, incluso si no hubo incidencias, como antes. Un subdominio configurado recibe un correo solo si se procesó alguna página suya o hubo un hallazgo procedente de ella. Cada correo adjunta **únicamente sus CSV filtrados**, con asunto que identifica su ámbito. Los CSV globales permanecen en `reports` para auditoría local; no se adjuntan al correo principal cuando hay rutas configuradas. Las métricas de peticiones y throttling del pie son totales del proceso y se indican así, porque una petición a un destino compartido no puede atribuirse limpiamente a un único subdominio.

En `[report]`, `csv_format = es` genera los CSV con `;` (predeterminado, útil para Excel con configuración española); `csv_format = en` utiliza `,`. Afecta a los CSV detallado, agrupado y de actualización puntual de contexto. Las fechas siguen en formato ISO 8601 y los encabezados mantienen sus nombres para no cambiar el esquema. Los CSV siguen codificados como UTF-8 con BOM. Si el `config.ini` instalado aún no tiene `[report]`, se usa `es` automáticamente.

## Preparar un repositorio GitHub

El paquete ZIP incluye `smtp.env` **solo con valores ficticios de prueba**. `.gitignore` excluye ese archivo y cualquier `config.ini` local al ejecutar `git add .`; la plantilla publicable es `smtp.env.example`. Para subir el proyecto, descomprimir el ZIP, entrar en `upv-broken-links-checker`, crear un repositorio vacío en GitHub y ejecutar:

```bash
git init
git add .
git commit -m "Auditoría de enlaces UPV"
git branch -M main
git remote add origin https://github.com/USUARIO/REPOSITORIO.git
git push -u origin main
```

Sustituir `USUARIO/REPOSITORIO` por el repositorio creado. Para usar el correo de verdad, crear `smtp.env` con las credenciales reales **en el servidor**; el de prueba incluido en el ZIP no puede autenticar.

## Instalación en Linux

En el servidor `groq`, con `/opt/analytics` y el usuario `analytics-svc` ya existentes, sigue [DEPLOY_LINUX.md](DEPLOY_LINUX.md). El instalador deja esta aplicación en `/opt/broken_links_checker`, independiente de Analytics. Copia los archivos al servidor, ejecuta `sudo bash install_linux.sh`, configura `config.ini` y `smtp.env`, prueba una ejecución pequeña y habilita cron con `sudo bash install_linux.sh --enable-cron`. La prueba `smtp.env` del ZIP no se instala como credencial.

El cron diario reparte la cobertura entre ejecuciones. `max_pages_per_run = 10000`, `max_pending_links_per_run = 1000` y `max_http_requests_per_run = 50000` son **techos**, no promesas: el tercero cuenta intentos, redirecciones, reintentos y solicitudes a robots.txt. Los enlaces pendientes vencidos se reintentan primero, con un tope independiente para reservar capacidad al descubrimiento de páginas. También se detiene si se agota la cola, si se alcanza `max_duration_hours = 20`, o si el servidor limita las peticiones. La página interrumpida por un límite conserva su estado pendiente y se reanuda en el siguiente cron. El lock evita solapamientos. Se recorren páginas HTTP(S) **solo de `upv.es` y sus subdominios**, con o sin parámetros, hasta el nivel configurado. Se comprueban todos los enlaces salientes de esas páginas, incluidos destinos externos y los destinos UPV fuera del último nivel, pero no se siguen enlaces de páginas externas. Las extensiones binarias se comprueban como enlace y no se exploran como página. Los hosts locales o privados se omiten por defecto; `allow_private_hosts = yes` no amplía los dominios que se rastrean. En un destino externo se comprueba el estado HTTP y las redirecciones, sin descargar su cuerpo HTML para buscar enlaces o soft-404 específicos de UPV.

Cada petición al mismo host se separa al menos `min_interval_seconds = 1.0` segundos, y las peticiones globales al menos `min_global_interval_seconds = 0.2`. Ante un 429 o 503 se respeta `Retry-After` (segundos o fecha HTTP); sin esa cabecera se aplica una espera exponencial corta. Si la espera supera `max_retry_wait_seconds = 30` o fallan tres intentos, ese host se pausa durante el resto de la ejecución; el cron siguiente lo vuelve a probar. Las páginas que no se pudieron revisar se reintentan al día siguiente. Los 429/503, otras respuestas 5xx, 401/403/408 y errores de red se cuentan como inciertos, no como enlaces rotos. El CSV detallado incluye nivel, fecha, origen, destino, ancla, resultado y `contexto_html`. Este campo combina la posición estructural (`navegacion`, `cabecera`, `pie`, `lateral` o `contenido`) con pistas como `indicio_movil`, `oculto_html`, `aria_hidden` u `oculto_inline`. Es una pista obtenida del DOM, no una comprobación de visibilidad real en un móvil; `sin_datos` indica enlaces guardados antes de esta versión. El CSV agrupado reúne destinos idénticos y muestra los contextos observados, el número de páginas afectadas y un origen de ejemplo. Un robots.txt con 4xx se trata como inexistente; con 5xx o error de red el host se omite temporalmente.

La tabla `pages` permite inspeccionar el tamaño descubierto por nivel (`SELECT level,count(*) FROM pages WHERE level IS NOT NULL GROUP BY level;`). La tabla `level_rounds` indica qué ronda está activa y cuándo puede empezar la siguiente. SQLite evita rastrear de nuevo una URL completada en su ronda aunque aparezca en distintas páginas de origen. Las páginas cuyo propio HTML no se pudo descargar se reintentan al día siguiente; un enlace saliente incierto no vuelve a poner la página en cola. La tabla `pending_links` contiene los destinos inciertos, que se vuelven a probar al día siguiente. Si entonces se confirma un enlace roto, aparece en el informe de esa ejecución con el origen y ancla guardados. Los enlaces de páginas que desaparecen se sustituyen al volver a visitarlas. Al actualizar una base SQLite creada por una versión anterior se conservan niveles y rondas. Las páginas que ya estaban pendientes se revisan una última vez con la nueva lógica: los enlaces inciertos antiguos no estaban guardados por separado.

Al actualizar desde una versión que recorría dominios externos, el primer arranque elimina de `pages` las páginas externas y sus enlaces **salientes** antiguos. Conserva los enlaces desde páginas UPV hacia esos destinos, sus comprobaciones en `checks`, las rondas de los niveles y los resultados pendientes que aún tengan un origen UPV. Esta migración se hace una sola vez bajo el mismo bloqueo de ejecución.

### Actualizar el contexto antiguo sin reiniciar las rondas

Después de que termine el rastreo en curso, ejecuta `venv/bin/python broken_links_checker.py --config config.ini --backfill-context`. Usa el mismo fichero de bloqueo, los límites de tiempo, solicitudes y ritmo, y respeta robots.txt. Descarga **solo el HTML de la página de origen** (más las solicitudes necesarias a robots.txt y las redirecciones) y actualiza el contexto de los enlaces antiguos que todavía aparecen con el mismo destino y texto; no comprueba sus destinos, no crea nuevos enlaces, no modifica `pages`, `checks`, `pending_links` ni `level_rounds`, y no envía correo. Se limita a `max_context_backfill_pages = 1000` páginas por invocación. Si quedan más páginas, repite el comando cuando termine. Los fallos temporales se reintentan al día siguiente; el estado de avance queda en `context_backfill` y se crea un CSV `reports/contexto_pendiente_*.csv` con actualizados y no encontrados. Un enlace que haya desaparecido o cambiado de texto permanecerá en `sin_datos` hasta el siguiente rastreo normal; no se presenta como contexto confirmado. La orden sale con código 2 si hay un rastreo en curso.

`db_retention_days = 5` elimina resultados de comprobación antiguos y páginas no visitadas desde hace ese plazo, junto con los enlaces que solo pertenecían a ellas. Conserva la cola activa y la portada para que un rastreo interrumpido pueda continuar. Con `level_schedule = 0:1;1:1;2:1;3:4`, cinco días superan el intervalo máximo de cuatro. El valor debe ser al menos el mayor intervalo **efectivo** de `level_schedule`; de lo contrario la ejecución se detiene con un error de configuración. Si un nivel pide menos días que el anterior, el script utiliza los días del anterior y lo registra en el log. Los CSV generados en `reports` no están sujetos a esta retención de SQLite. El borrado de registros no reduce necesariamente el tamaño físico del archivo SQLite: para recuperar ese espacio hay que compactarlo con `VACUUM` en una ventana sin rastreos activos.

Las cifras de 2.500 páginas en nivel 2 y 24.000 en nivel 3 obtenidas desde el mapa web **no se trasladan directamente** a niveles definidos desde la portada, especialmente cuando se incluyen otros dominios. Tras las primeras rondas, usar los recuentos reales de `pages` para calibrar `max_pages_per_run`. El tope de 10.000 y el límite de 50.000 peticiones pueden alargar una ronda; el programa no fuerza la cadencia mediante más solicitudes. Los niveles limitan **qué páginas se rastrean**, no cuántos enlaces se comprueban en cada una. Una página cuyo contenido requiere JavaScript, autenticación o está excluida por robots no puede verificarse íntegramente con este rastreador HTTP.

El rastreador no ejecuta JavaScript de analítica, pero sus peticiones sí aparecen en logs, estadísticas de servidor y métricas de CDN. Excluir el `User-Agent` configurado (`UPV-BrokenLinks-Audit/1.0`) o la IP fija del cron en esas herramientas; el script no puede excluirse por sí solo de métricas generadas por el servidor.
